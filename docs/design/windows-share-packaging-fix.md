# Windows 分享入口的打包缺漏（1.0.5）

用户反馈两台电脑安装后，微信的「转发到其他应用」未出现微信流。

代码审查确认两处缺漏：分享组件没有嵌入 `<msix>` 包身份声明；生成的 `resources.pri` 只进入 MSIX，没有复制到稀疏包的外部安装目录。旧的安装验证只检查 `Get-AppxPackage` 返回值，无法检出 EXE 未取得身份的问题。这些是已确认的打包缺陷，尚不能据此认定两台远端机器的微信菜单问题已完全解决。

修复方式：

- 分享组件使用独立的原生清单，嵌入对应的 publisher、packageName 和 applicationId，并保留 PerMonitorV2。
- 安装器构建时根据实际签名证书生成分享组件清单，校验其 EXE 内嵌身份与最终 MSIX 一致。
- 将同一次生成的资源索引部署到外部目录，校验内外索引哈希一致及必要图标存在；开发注册脚本同步修正。
- 注册后以安装用户启动 `--registration-check`。这个模式只查询当前进程身份，不创建收件箱、不启动驻留服务、不打开选择器。缺少身份或取得错误身份时，安装返回失败并写入注册日志。
- 诊断工具增加资源索引和运行时身份检查，旧版本不运行新探针，避免将旧组件误启动为驻留服务。

验证：旧的 1.0.1 安装目录被身份一致性检查拒绝；缺少外部索引、索引内容不一致的测试载荷均被拒绝；完整载荷通过检查。本机通过正式 Setup 从 1.0.1 升级到 1.0.5，退出码为 0，注册状态为 Ok，实际启动探针取得 `WeChatBridge.Windows.ShareTarget_1.0.5.0_neutral__k2gw8zhv15c4m` 和 `WeChatBridge.Windows.ShareTarget_k2gw8zhv15c4m!Share.Hub`。升级后 216 个原有文件哈希未变；重新启动后台应用后，仅运行日志正常追加，215 个用户数据与配置文件哈希未变。新版诊断工具通过 Windows PowerShell 5.1 验证。

## 1.0.6：远端分享菜单对照

2026-10-04 在 192.168.3.18（Windows 11 23H2，22631）通过 SSH 对照本机（26100）。两边微信 4.1.15.13 的 EXE 哈希一致；1.0.5 分享组件取得正确包身份，名称、图标与资源索引一致，目标机普通权限进程也能读取这些信息。

逐项改变同一分享包，用户每次彻底退出并重启微信后的反馈：

| 文件类型声明 | AppListEntry | 微信菜单 |
| --- | --- | --- |
| SupportsAnyFileType | none | 横线 |
| SupportsAnyFileType | 默认可见 | 横线 |
| 明确 .zip | 默认可见 | 出现微信流；资源管理器共享面板也有微信流 |
| 明确 .zip | none | 又变成横线 |

根据上述反馈，1.0.6 尝试显式声明 `.zip` 并移除 `AppListEntry="none"`，保留 `StorageItems`；增加相应构建检查。但正式包安装后用户仍反馈横线，因此这两项不能认定为最终根因或有效修复。各次临时构建的 PRI 也发生变化，对照并未完全隔离变量。可见入口可能让开始菜单多显示一个分享组件应用。

验证限制：上述对照验证了入口显示，尚未验证用户真实聊天 ZIP 从微信到目标应用的完整转发。不能把安装成功、运行时身份正确或入口出现等同于完整转发成功。

正式 1.0.6 自包含 Setup 已在该目标机完成升级，退出码 0；主程序为 1.0.6.0，注册包为 1.0.6.0、状态 Ok，实际 helper 探针取得正确身份；正式包清单为可见入口及 `.zip`。核心测试 287 项、应用测试 8 项通过；隐藏入口和仅任意类型两个负例均被构建检查拒绝。两个临时诊断计划任务已移除。

用户重启微信后确认正式 1.0.6 仍为横线。升级前的 4 个用户配置与数据文件哈希未变化。不要将此安装包作为已修复版本交付。

提交记录追溯：`9d0511b` 在名称中使用 U+2060 避开微信品牌子串过滤，并修正 UTF-8 清单读取；`70b6ae7` 生成资源索引并同步外部图标。开发脚本和安装器均以 `Add-AppxPackage -Path ... -ExternalLocation ...` 注册；本机及目标机日志确认注册成功且目标用户正确。当前没有证据表明漏执行注册命令。成功临时包主 PRI 为 3240 字节，正式包为 3296 字节，需进一步隔离资源生成差异。

后续回归：保留 1.0.6 程序文件，将之前成功临时包的内容原样重新封包（仅更新包版本至 1.0.6.1），仍反馈横线，无法复现最初成功结果；随后恢复目标机正式 1.0.6 注册及匹配 PRI。本机最初进程早于 1.0.5 安装，但用户彻底重启本机微信后仍能显示入口，因此不能把本机可见归因于旧进程缓存。两机 `WeChatAppEx.exe` 以及该宿主加载的 9 个 RadiumWMPF 模块哈希相同。两机名称均保留 U+2060；排查尚未收敛。

## 1.0.7：用户指定的中性名称重装测试

用户在目标机安装 WorkBuddy 后，其入口能够显示，微信流仍不可见。单独重新注册微信流、使用 WorkBuddy 的四类格式声明、仅临时改成“聊天桥”均未解决。临时包随后撤回，没有据此发布格式兼容性修复。

按照用户要求，Windows 测试版统一改名为“聊天桥”，版本升至 1.0.7；分享包身份改为 `ChatBridge.Windows.ShareTarget`，主程序、分享助手的产品描述、菜单、托盘、向导、安装器及开始菜单名称同步修改。代码命名空间、程序文件名、签名证书与现有数据目录保留，现有配置仍可读取。

已在目标机先完整卸载旧版 Setup、旧证书 MSI 及旧分享注册，卸载均成功，旧分享注册数量为 0；随后安装目标机桌面的 `ChatBridge-1.0.7-Windows-Setup.exe`。安装日志退出码 0；主程序 1.0.7.0、产品名聊天桥，新分享包 1.0.7.0 状态 Ok，实际助手身份探针取得 `ChatBridge.Windows.ShareTarget_k2gw8zhv15c4m!Share.Hub`。6 个已有配置与数据文件哈希未变。构建校验通过，核心 287 项及应用 8 项测试通过，安装包签名有效。

用户彻底退出并重启微信后反馈：仍只有 WorkBuddy，没有“聊天桥”。因此本次中性名称及全新包身份的干净重装没有解决问题；不能作为修复版本发布。真实转发尚未验证。
